# OZARU 0.1.x audit

Audited state: ozaru 0.1.6, on 2026-11-02.

Everything below was checked against the code, the dependency tree or by running
tests. Performance figures come from a single Linux x86_64 machine with 12 cores.

## 1. Current architecture

```text
Python (user code)
   │  import ozaru
   ▼
ozaru/__init__.py           generated by maturin: from .ozaru import *
ozaru/__init__.pyi          type hints (ozaru.pyi in the repository)
   │
   ▼
ozaru.abi3.so               crate `ozaru` (src/lib.rs, ~200 lines, PyO3 0.29, abi3-py310)
   │  1. releases the GIL (py.detach)
   │  2. reads the file with std::fs::read and maps I/O errors
   │  3. opens the PDF in a new thread with an 8 MiB stack
   │  4. extracts page by page, resuming in another thread after a panic
   │  5. takes the GIL back and emits a PageWarning for each failed page
   ▼
pdf_oxide 0.3.78            ALL of the PDF processing
```

The repository has no Python code of its own: only the `__init__.py` that maturin
generates and the `ozaru.pyi` type hints.

## 2. Dependencies and what they do

### Direct dependencies

| Crate | Version | Role in ozaru |
|---|---|---|
| `pyo3` | 0.29.3 | Python bindings |
| `pdf_oxide` | 0.3.78 | All of the PDF processing |

### What ozaru actually uses from `pdf_oxide`

Only four functions:

| Function | Use |
|---|---|
| `PdfDocument::from_bytes` | Parse the document |
| `PdfDocument::is_authenticated` | Detect PDFs that need a password |
| `PdfDocument::page_count` | Count pages |
| `PdfDocument::extract_text(i)` | Text of one page, with table detection on by default |

### What `pdf_oxide` brings along

- **Full tree:** 173 crates, 172 of them through `pdf_oxide`.
- **Size of `pdf_oxide`:** about 452,000 lines of Rust in `src/`, with 99
  occurrences of `unsafe`.
- **Features ozaru doesn't use:** editing, rendering, signatures, XFA forms, OCR,
  Office conversion (`office_oxide`), HTML/CSS (`taffy`) and PDF/A.
- **Their dependencies:** `image`, `jpeg-decoder`, `zune-jpeg`, `brotli`, `zip`,
  `quick-xml`, `regex`, `serde_json`, `chrono`, `uuid`, `env_logger` and
  `subsetter`. ozaru doesn't need any of them.
- **Enabled features:** `default`, which means `icc` (with `qcms`) and
  `legacy-crypto`.
- **Resulting size:** the compiled `libozaru.so` is 23 MB, and each wheel is about
  8 MB.

### PDF work delegated to `pdf_oxide` today

ozaru implements none of it. All of it lives in `pdf_oxide`:

- **Reading the document:** lexer, object parser, xref table, xref streams, object
  streams and repair of damaged xrefs.
- **Streams:** compression filters and predictors.
- **Security:** decryption, with RC4 and AES through `aes`, `cbc`, `md-5` and `sha2`.
- **Structure:** page tree and resources.
- **Fonts:** encodings, CMaps and ToUnicode.
- **Content and text:** operator interpretation, reading order, tables, RTL and
  vertical CJK.

## 3. Current features

| Feature | Behavior |
|---|---|
| `extract_text(path)` | Full text, with pages separated by `\f`. A page that fails is left empty and emits `PageWarning`. |
| `page_count(path)` | Number of pages, even for password-protected PDFs. |
| `PageWarning` | Subclass of `UserWarning` with `page` (starting at 1) and `reason`. |
| Paths | Accepts `str` and `os.PathLike`. |
| File errors | The same exceptions as `open()`, with `errno` and `filename`. |
| Damaged PDF | `ValueError`, without affecting later reads. |
| Concurrency | Releases the GIL. 4 threads take 4.9 s against 9.8 s in series. |

## 4. Limitations

1. **No password:** there is no `password` parameter, so PDFs that need one can't
   be read.
2. **No OCR:** scanned PDFs return little or no text.
3. **Files on disk only:** `bytes` in memory can't be read.
4. **No `Document` object:** calling `page_count` and then `extract_text` parses
   the PDF twice.
5. **Plain text only:** no positions, fonts, images, metadata or structure.
6. **Free-threaded Python:** wheels are `abi3`, so they don't work on 3.13t or
   3.14t. There, pip builds from source and needs Rust.
7. **No wheels for:** Windows ARM64, Linux armv7, s390x and ppc64le.

## 5. Technical problems

| # | Problem | Impact | Severity |
|---|---|---|---|
| P1 | **The PDF engine isn't ozaru's.** All correctness depends on an external project of 452,000 lines. | Bugs such as the `char boundary` panic in `document.rs:25363` can only be worked around, not fixed. | High |
| P2 | **`pdf_oxide` keeps per-thread state** (`RESOLVING_STACK`, `RECURSION_DEPTH`) that a panic leaves dirty. | Forces one thread per call, plus another after each panic. | High, contained |
| P3 | **`pdf_oxide` panics are printed to the terminal** (`thread '<unnamed>' panicked at…`). | They clutter the user's output even when the result is correct. | Medium |
| P4 | **Memory:** the file is read whole, and each reading thread gets a copy. | Peak memory of twice the PDF size, plus one copy per panic. | Medium |
| P5 | **Size:** 8 MB wheels and a 23 MB `.so`, mostly from features ozaru doesn't use. | Heavier downloads and installs. | Medium |
| P6 | **CI only runs tests on Linux x86_64.** macOS, Windows, aarch64 and musl wheels are built but never tested. | A platform-specific bug would reach PyPI. | High |
| P7 | **No Rust tests, no fuzzing in CI and no benchmarks.** | There is no safety net for the future engine. | High for the engine |
| P8 | **The text depends on `pdf_oxide`'s internal heuristics**, such as table detection or RTL ordering, which ozaru neither controls nor documents. | Output may change when `pdf_oxide` is upgraded. | Medium |
| P9 | **Test names mix Spanish and English.** | Cosmetic. | Low |
| P10 | **`backfill-releases.yml` is still in the repository** after doing its job. | None. | Low |

Results of 0.1.6 against the published 0.1.4, on 3000 damaged PDFs:

| Result | PDFs |
|---|---|
| Same text, no warning | 1578 |
| Same text, but **now with a warning** (pages used to be lost silently) | 1159 |
| `ValueError` before, **pages recovered now** | 36 |
| Same error as before | 227 |
| Different text on a page without a warning | 0 |

Speed is similar in both versions: 2.4 s to 2.7 s for a 2000-page PDF, with a single
run of each. More precise claims need repeatable benchmarks.

## 6. Components to replace

To make PDF processing belong to ozaru:

| Component | Today | Replacement |
|---|---|---|
| Lexer, objects and parser | `pdf_oxide` | `ozaru-engine::syntax` |
| Xref, xref streams, object streams and repair | `pdf_oxide` | `ozaru-engine::xref` |
| Filters and predictors | `pdf_oxide` | `ozaru-engine::filters`, with Flate decompression from a helper crate |
| Decryption (Standard Security Handler) | `pdf_oxide` | `ozaru-engine::security`, with RustCrypto primitives |
| Catalog and page tree | `pdf_oxide` | `ozaru-engine::document` |
| Fonts, encodings and CMaps | `pdf_oxide` | `ozaru-engine::fonts`, with `ttf-parser` for embedded fonts |
| Content and text | `pdf_oxide` | `ozaru-engine::content` and `ozaru-engine::text` |

These don't need replacing:

- **`pyo3`**, which isn't a PDF engine.
- **Helper crates for compression and cryptography**, which the project rules allow.

## 7. Migration risks

| Risk | Why it matters | Mitigation |
|---|---|---|
| **Lower text quality** | `pdf_oxide` handles hard cases: fonts without ToUnicode, CJK, RTL and tables. A new engine will start out worse. | Don't switch engines until measured criteria are met on a corpus. Until then, `pdf_oxide` stays the published engine. |
| **Malformed real-world PDFs** | Many real PDFs break the standard, with broken xrefs or wrong offsets. | Repair mode from phase 3, and a corpus that includes corrupted PDFs. |
| **Encryption** | Many PDFs are encrypted with an empty user password. Without decryption, the text is unreadable. | Move basic decryption up to phase 4 instead of leaving it for the end. |
| **Security** | A PDF parser handles untrusted data, with risks of decompression bombs, infinite recursion and reference cycles. | No `unsafe`, configurable limits and continuous fuzzing. |
| **Duration** | It's a project of years, not weeks. | Small phases with verifiable criteria, and nothing incomplete exposed. |
| **Changes for users** | Switching engines can change spaces, line breaks and text order. | Switch one function at a time, document it in the changelog and release it as a 0.x.0 version. |
| **Licenses of the corpus and data** | Test PDFs and some tables, such as the Adobe Glyph List or the predefined CMaps, have their own licenses. | Check every license before adding anything to the repository. |
| **Reference tools** | PyMuPDF is AGPL. | Use it only in local or CI comparison tests, never as a distributed dependency. |

## 8. Proposed architecture

Summary. The details are in [engine.md](engine.md).

- **Separate crates:** a Cargo workspace with an `ozaru-engine` crate in pure Rust,
  without PyO3, and the current `ozaru` crate as the Python layer.
- **`ozaru-engine`:**
  - `#![forbid(unsafe_code)]`.
  - No global or per-thread state, and `Send + Sync` types, so no thread per call
    is needed.
  - Typed errors and recoverable diagnostics. Diagnostics become Python warnings,
    like today's `PageWarning`.
- **Migration side by side:** the engine grows next to `pdf_oxide` and is compared
  against it and against pypdf or PyMuPDF in tests. None of them is used as an
  internal engine.
- **Engine switch:** it happens when the engine meets the criteria, and then
  `pdf_oxide` is removed.

## Recommended improvements to the current project

They don't depend on the engine, and are listed by priority:

1. **Test the wheels on each platform (P6):** after building, install the wheel and
   run `pytest` on Windows, macOS and Linux aarch64.
2. **Add fuzzing and Rust tests (P7)**, starting with phase 1 of the engine.
3. **Silence or redirect `pdf_oxide` panic messages (P3)**, only while it's still
   in use.
4. **Remove `backfill-releases.yml` (P10).**
